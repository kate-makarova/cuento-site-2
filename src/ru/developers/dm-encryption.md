<p class="docs-lead">Личные сообщения в Cuento шифруются сквозным шифрованием прямо в браузере. Сервер хранит только зашифрованный текст — он никогда не видит содержимое сообщений в открытом виде, а приватный ключ, необходимый для расшифровки, никогда не покидает устройство пользователя.</p>

## Архитектура ключей

Каждый пользователь имеет пару RSA-4096 ключей, которая генерируется полностью в браузере с помощью Web Crypto API. Публичный ключ хранится на сервере. Приватный ключ тоже хранится на сервере, но **в зашифрованном виде под паролем пользователя** — сервер держит зашифрованный blob приватного ключа, но не пароль, которым тот зашифрован.

При входе в систему браузер:
1. Загружает зашифрованный blob приватного ключа (`private_key`, `salt`, `iv`) через `GET /user/private-key`.
2. Генерирует AES-GCM-ключ из пароля пользователя с помощью PBKDF2.
3. Расшифровывает blob приватного ключа в браузере.
4. Хранит полученный `CryptoKey` в памяти в `UserService.privateKey()` — он никогда не записывается в localStorage и не отправляется на сервер.

## Шифрование сообщения (отправка)

Для каждого сообщения генерируется свежий AES-GCM-256 ключ. Последовательность в `DirectChatService.buildMessagePayload`:

1. Генерируется случайный AES-GCM-256 ключ и 12-байтовый IV.
2. Полезная нагрузка сообщения (JSON-строка `{ "text": "<BBCode>", "html": "<скомпилированный HTML>" }`) шифруется AES-GCM.
3. Сырые байты AES-ключа экспортируются и оборачиваются отдельно: **публичным ключом автора** (`key_author`) и **публичным ключом получателя** (`key_receiver`) — с использованием RSA-OAEP/SHA-256.
4. На сервер отправляется POST `{ chat_id, ciphertext, iv, key_author, key_receiver, author_key_id, receiver_key_id }`.

Сервер хранит все эти поля как есть — он не может прочитать `ciphertext` без AES-ключа, а восстановить AES-ключ без одного из RSA приватных ключей невозможно.

## Расшифровка сообщения (получение)

API возвращает каждое сообщение с полем `key` — какой из ключей (`key_author` или `key_receiver`) принадлежит текущему пользователю, определяется на бэкенде. `DirectChatService.decryptMessage`:

1. Использует RSA приватный ключ из памяти для разворачивания `key` (RSA-OAEP) → сырые байты AES-ключа.
2. Импортирует AES-ключ и расшифровывает `ciphertext` с сохранённым `iv`.
3. JSON-парсит открытый текст → `{ text, html }`. Устаревшие сообщения (до 2026-10-22) хранили сырой BBCode вместо JSON; если `JSON.parse` выбрасывает ошибку, `decryptMessage` вызывает `parseBBCode` напрямую.

## Версионирование ключей

Каждая строка сообщения хранит `author_key_id` и `receiver_key_id` (FK → `public_keys.id`). В таблице `public_keys` есть колонка `is_active`; у каждого пользователя в любой момент времени активен ровно один ключ.

При загрузке сообщений `decryptMessage` сравнивает ID ключа сообщения с `UserService.publicKeyId()` (ID активного публичного ключа пользователя). Если ID не совпадают, сообщение было зашифровано для предыдущей пары ключей — возвращается `{ inaccessible: true }`. Интерфейс показывает уведомление «зашифровано устаревшим ключом» вместо содержимого.

## Коды восстановления

Поскольку приватный ключ зашифрован под паролем пользователя, пользователь может сбросить пароль со страницы входа — если у него есть **код восстановления**. Браузер хранит по одной зашифрованной копии приватного ключа на каждый код восстановления, и каждая завёрнута под отдельный AES-ключ, производный от этого кода. Использование кода восстановления перешифровывает приватный ключ под новым паролем без замены самой RSA-пары. Все существующие сообщения остаются читаемыми.

Каждый код восстановления можно использовать ровно один раз; после использования в строке `recovery_codes` выставляется `date_used`. Пользователи могут перегенерировать коды в настройках аккаунта в любой момент, пока авторизованы.

## Почему замена RSA-пары уничтожает старые сообщения

**Смена пароля** только перешифровывает обёртку приватного ключа — сама RSA-пара остаётся прежней, поэтому сообщения, зашифрованные для старого публичного ключа, по-прежнему расшифровываются тем же приватным ключом. Это обычный путь смены пароля и использования кодов восстановления.

**Смена RSA-пары** — другая операция. Она происходит в двух случаях:

- **Административный сброс пароля** (`POST /admin/users/:id/reset-password`): При нём деактивируются все существующие строки публичных и приватных ключей (`is_active = false`) и создаётся новая запись сброса. Когда пользователь завершает процедуру, браузер генерирует новую RSA-пару и сохраняет новый публичный ключ. Все предыдущие сообщения были зашифрованы для старого публичного ключа — соответствующий приватный ключ деактивирован и утрачен. `decryptMessage` возвращает `inaccessible: true` для каждого из них.
- **Удаление аккаунта** (`POST /user/wipe`): Удаляет DM пользователя вместе со строками приватных ключей.

Сами сообщения при административном сбросе не удаляются — они остаются в базе данных — но навсегда нечитаемы, поскольку не существует ни одной копии RSA приватного ключа, способной развернуть поля `key_author` / `key_receiver`.

## Таблицы базы данных

| Таблица | Назначение |
|---|---|
| `public_keys` | RSA публичные ключи; `is_active` помечает текущий ключ пользователя |
| `private_keys` | Зашифрованные AES blob'ы RSA приватных ключей; `is_active = true` для копии под паролем; `is_active = false` для копий под кодами восстановления (ссылаются через `recovery_code_id`) |
| `recovery_codes` | Хэшированные коды восстановления; `date_used` выставляется при использовании; `security_code` — одноразовый токен в процессе сброса пароля |
| `direct_chat_messages` | На каждое сообщение: `ciphertext`, `iv`, `key_author`, `key_receiver`, `author_key_id`, `receiver_key_id` |
